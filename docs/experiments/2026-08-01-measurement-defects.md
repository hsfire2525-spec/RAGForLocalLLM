# 測定側で見つけた欠陥（2026-08-01）

**本リポジトリで最も学びが大きかったのは、手法の改善ではなく測定側の欠陥だった。**
6件すべてが「例外は出ないが、静かに間違った数字を出す」型で、実物を動かすまで
気付けなかった。同じ轍を踏まないために記録する。

共通する性質:

- **テストは通っていた。** 合成データでは再現しない条件だった
- **数字は出ていた。** もっともらしい値なので、疑う理由がなかった
- **見つかったのは実物を動かしたとき。** 実コーパス・実モデル・実利用者の
  いずれかが要った

## 1. 自動採点が正答を誤答と判定していた（最大）

**症状**: ベースラインの正答率が 0.667 と出た。

**発見**: 「誤答」10件を目視したところ、**大半はモデルが正しく答えていた**。

```
q012 gold: 知っているもの、持っているもの、本人自身に関するもの
     pred: 「知っているもの」「持っているもの」「本人自身に関するもの」である  ← 正しい
```

**原因は3つ。すべて「モデルの答え方」と「gold の書き方」のズレ。**

| 原因 | 内容 |
| --- | --- |
| 列挙の完全一致 | モデルは列挙を裸の単語で返さず文に埋め込む。要素の完全一致を要求すると 0 点 |
| 句の短答に char F1 の経路が無い | 短答には単語（「経営者」）と句（「利用者認証を…行う技術」）があり、適切な指標が違う |
| char F1 が冗長さを罰する | 4B級モデルは根拠や補足を添えるため予測が gold の3〜4倍になり、適合率が落ちる |

**対処**: 列挙は包含で対応付ける。短答は gold の長さで指標を切り替える
（単語に char F1 を使うと「経営」が「経営者」に 0.8 で誤って正答になる）。
冗長さには gold と同じ幅の窓を予測上で滑らせ、最も一致する位置で測る。

**結果**: 正答率 0.667 → 0.905（同一の回答を再採点）。列挙型は 0.20 → 1.00。

**緩めすぎていないことの確認**: 「もっともらしいが誤り」の回答を10件用意して
食わせ、10件すべてが誤答と判定されることを確かめた（資産価値と復旧コストの
足し算、パスワード・合言葉・秘密の質問、など）。回帰テストに含めた。

> **教訓**: 自動採点は「正しく採点できているか」を別途確かめないと信用できない。
> 設計では人手検査の一致率で検出する想定だったが、実際にはランの中身を
> 読んで先に気付いた。**指標を作ったら、その指標が正しいかを測る手段も要る。**

## 2. チャンカーが文書メタデータを捨てていた

**症状**: gold のページ・節アンカーが一切解決できない。`add_section_path` も
出典表示も無効。

**原因**: `_make_chunk` がメタデータを新規に組み立てており、`doc.metadata` を
引き継いでいなかった。`page` / `section_path` がチャンクに届いていない。

**なぜテストで見つからなかったか**: 合成コーパス（`data/corpus/sample/`）に
**ページの概念が無い**。実PDFで `rag gold draft` を動かして初めて露見した。

> **教訓**: 合成データは「実データが持つ属性のうち、テストが使うものだけ」を
> 持つ。実データにしかない属性（ページ、節、表）を通る経路は、実データでしか
> 検証できない。

## 3. `corpus_info` が単一ファイルを前提にしていた

**症状**: ディレクトリ形式のコーパスで `IsADirectoryError`。ランレコードが
一切書けない。

**原因**: インデックス署名側は `sha256_of` とディレクトリ用の実装を
使い分けていたのに、環境情報側は単一ファイルしか想定していなかった。
**同じ「コーパスの同一性」を2箇所で別々に実装していた。**

**対処**: `env.corpus_signature` に統合。

## 4. `rag footprint` が常駐量を 0MB と表示していた

**症状**: 埋め込み器の増分が 0.0MB。

**原因**: モデルを遅延読み込みする設計（グローバルなシングルトンを持たない
制約の帰結）のため、構築直後には何も読み込まれていない。

**対処**: 実際に使わせてから測る。実測値 **1,460MB**。

> **教訓**: 測定ツール自体を実物に対して動かさないと気付けない型の欠陥。
> 「0 が出た」は「影響が無い」ではなく「測れていない」かもしれない。

## 5. `rag review` の表示が誤診を招いた

**症状**: 人手検査で「根拠は取れているのに棄権」というコメントが付いたが、
実際にはその質問の根拠は**検索できていなかった**。

**原因**: 画面に `根拠=[gold_chunk_ids]` と gold の正解キーを表示しており、
検査者がそれを「システムが持っていた根拠」と読んだ。

**対処**: 取得順位と「プロンプトに入ったか」を明示するようにした。

```
q019: 根拠を取得できず（上位5件に無し。棄権や誤答は検索側の問題）
q025: 根拠を4位で取得（ただしプロンプトには入っていない）
```

**この修正が、より重い問題を暴いた。** q025 の表示から、検索できた根拠が
コンテキスト予算で捨てられていることが分かり、42問中38問で計75チャンクが
落ちていると判明した（→ [ベースライン構築](2026-08-01-ipa-baseline.md) の 4）。

> **教訓**: 人手検査の画面は「人が正しく診断できるか」で設計する。
> 表示が曖昧だと、人手判定という最も信頼していた情報源が汚染される。

## 6. 全問正解でブートストラップ信頼区間が縮退した

**症状**: 正答率 1.000 に対し信頼区間 `[1.000, 1.000]`。

**原因**: 標本に分散が無いとどのリサンプルも同じ平均になる。
**「絶対に 1.0」という主張になってしまう。** 42問中42問正解でも、
真の正答率が 0.92 である可能性は十分にある。

**対処**: 二値の指標は Wilson スコア区間を使う。`1.000 [0.916, 1.000]`。
差の系列は割合ではないので従来どおりブートストラップ（全件 0 のときに
Wilson を使うと「割合 0」の非対称な区間になってしまうため、明示的に分けた）。

## 番外: 比較レポートが指標の向きを知らなかった

棄権率の低下を「悪化」と表示していた。`error_rate` は小さいほど良く、
`accuracy` は大きいほど良いが、**棄権率はどちらとも言えない** —
棄権は誤答を避ける機能であり、良し悪しは gold の構成と目的次第。
方向（増加/減少）だけ示し、判断は人に委ねるようにした。

## まとめ

6件のうち、**5件は実物（実PDF・実モデル・実利用者）を動かして初めて
露見した**。テストは全件通っていた。

| 何が要ったか | 該当 |
| --- | --- |
| 実PDF（ページ・節・表を持つデータ） | 2 |
| 実モデルの出力（冗長・言い換え） | 1 |
| 実行時のメモリ | 4 |
| 実際の利用者 | 5 |
| 境界値（全問正解） | 6 |
| 実運用の設定（ディレクトリ形式） | 3 |

**「テストが通っている」は「正しく測れている」を意味しない。**
評価基盤を作るプロジェクトでは、評価基盤自体を疑う手段を用意しておく必要がある。
本リポジトリでそれに当たるのは、人手検査の一致率、負例による確認、
そしてランの中身を実際に読むことだった。
