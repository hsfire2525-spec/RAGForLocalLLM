# IPAガイドラインでのベースライン構築（2026-08-01）

対象コーパス: IPA「中小企業の情報セキュリティ対策ガイドライン 第4.0版」（72ページ）
環境: 環境3（AMD Ryzen AI MAX+ 395 / 32コア / GTT 62GB）
モデル: `gemma-4-e4b-it`（LM Studio、`temperature=0`、`seed=42`）
gold: `qa_v1`（42問）→ `qa_v2`（60問）

## 問い

**性能の低いローカルLLMで、どこまで回答精度を上げられるか。**
そして、上げるために投資すべきなのはどこか。

## 結論を先に

**正答率 0.867 → 0.983（60問）。効いたのは検索とコンテキスト管理であり、
モデルの大型化ではない。** 4B級モデルのまま、以下の2つで届いた。

1. ハイブリッド検索（dense + BM25 を RRF で統合）
2. コンテキスト予算の是正（1536 → 2560）

**この2つは独立していない。** 検索を良くしても、その結果がプロンプトに
届かなければ精度にならない。実際、ハイブリッド検索単体では正答率の改善が
有意にならなかった（+0.048、CI が0を跨ぐ）。予算を直して初めて有意になった。

## 時系列

### 1. LLMを使わない下限を測る

`runs/20260801-111248-e5_extractive-253812671e55`（42問）

```
正答率 0.191   誤答率 0.714   棄権 適合率 0.000
検索 hit@5 0.853   MRR 0.748   引用解決率 1.00
```

語彙一致のみの回答器（`extractive`）で、検索は e5 + FAISS。
**回答不能8問に一度も棄権できていない。** 語彙が一致するだけで
「答えがある」と判断してしまうためで、設計が想定した
「話題は一致するが答えを含まない」型の難しさが実証された。

引用解決率 1.00 は、gold の引用文がすべて抽出テキストに解決したという意味。
Loader による情報損失は無い。

### 2. ベースライン（dense + LLM）

`runs/20260801-120754-baseline-4d7b74340f54`（42問）

```
正答率 0.905 [0.779, 0.962]   誤答率 0.000   棄権率 0.286
棄権 適合率 0.667   再現率 1.000
```

**誤答ゼロ。** 根拠が足りないときは棄権しており、取りこぼしの側に寄っている。
回答不能8問すべてに正しく棄権する一方、答えられる4問でも棄権していた。

質問タイプ別に見ると **table が 0.50** と突出して低い。原因は生成ではなく検索で、
「表4は何を示した表か」のような参照は質問文に意味的手がかりが乏しく、
埋め込みが効かない。

> ここに至るまでに、**自動採点の欠陥で正答率が 0.667 と出ていた**。
> 詳細は [測定側で見つけた欠陥](2026-08-01-measurement-defects.md)。

### 3. ハイブリッド検索

`runs/20260801-125911-hybrid-6856b96ff808`（42問）

| 指標 | baseline | hybrid | 差 [95%CI] | 判定 |
| --- | --- | --- | --- | --- |
| hit@5 | 0.853 | 0.971 | +0.118 [0.029, 0.235] | **改善** |
| MRR | 0.748 | 0.859 | +0.111 [0.022, 0.225] | **改善** |
| 正答率 | 0.905 | 0.952 | +0.048 [-0.071, 0.167] | 有意差なし |

**検索の差は検出できたが、生成の差は検出できなかった。** 検索指標は
ほぼ全問に効くのに対し、正答率は数問の変化でしか動かない。42問という規模の
限界であり、想定どおり。

判定が変わった6問を追うと、次の一手が見えた。

| qid | 変化 | 根拠の順位（baseline→hybrid） |
| --- | --- | --- |
| q019 表4 | 棄権 → **正答** | 圏外 → 取得 |
| q020 表1 | 棄権 → **正答** | 圏外 → 取得 |
| q033 身代金要求型 | 棄権 → **正答** | 圏外 → 取得 |
| q025 委託先 | 棄権 → **正答** | 4位（予算落ち）→ 1位 |
| q021 自社診断 | 正答 → **棄権** | 2位 → 3位（**予算落ち**） |
| q034 外注先 | 正答 → **誤答** | 1位 → 3位（**予算落ち**） |

**悪化2件はどちらも検索の失敗ではなく、コンテキスト予算による切り捨てだった。**

### 4. コンテキスト予算

まず `context_hit`（検索できた根拠がプロンプトまで生き残ったか）を指標に追加した。
`hit@k` との差がそのまま予算の損失になる。

```
hit@5 0.971  に対し  context_hit 0.912
→ 42問中38問で計75チャンクが予算で落ちていた（検索は5件、プロンプトは中央値3件）
```

LLM を使わない検索のみのスイープ（`sw_*` の5ラン）:

| 予算 | chunk | top_k | hit@5 | context_hit | context_precision |
| --- | --- | --- | --- | --- | --- |
| 1536 | 512 | 5 | 0.971 | **0.912** | 0.330 |
| **2560** | **512** | **5** | 0.971 | **0.971** | 0.218 |
| 4096 | 512 | 5 | 0.971 | 0.971 | 0.206 |
| 1536 | 256 | 8 | **0.882** | 0.882 | 0.190 |
| 2560 | 256 | 8 | **0.882** | 0.971 | 0.136 |

- 2560 で損失が消える。4096 に増やしても得るものはない
- **チャンクを小さくすると検索そのものが悪化する**（0.971 → 0.882）。
  マッチに必要な文脈が失われる。「小さく刻めば多く入る」は成立しない
- 代償は context_precision の低下（0.330 → 0.218）＝プロンプト内のノイズ増

`runs/20260801-131237-hybrid_budget-ead365065574`（42問）で **正答率 1.000**。
ノイズ増は、少なくともこの規模では害にならなかった。

### 5. gold が飽和したので難度を上げた

42問で 1.000 に達し、以降の手法を比較できなくなった。
`qa_v1` は凍結したまま、難問18問を足した `qa_v2`（60問）を作った。

追加した型: multi-hop、表の値の計算、表のセル参照、条件・例外、禁止・除外、
語彙が重ならない言い換え、**表に存在しない値を問う回答不能**（リスク値は
重要度×被害発生可能性なので 5 は取りえない。パターンで答えるモデルは「中」と答える）。

| 指標 | baseline | hybrid_budget | 差 [95%CI] |
| --- | --- | --- | --- |
| 正答率 | 0.867 | **0.983** | +0.117 [0.050, 0.200] **改善** |
| context_hit | 0.840 | 0.960 | +0.120 [0.020, 0.220] **改善** |

識別力は回復した。新規18問だけなら 17/18 正答で、multi-hop 4/4、
conditional 3/3、negation 3/3、lexical-gap 2/2、table-gap 1/1。
唯一の失敗は表の短いセル（「4 中」）を検索が引けなかったもの。

### 6. アブレーション（`rag sweep`）

`configs/sweeps/retrieval.yaml`、gold `qa_v2` 60問、基準 `hybrid_budget`。

| 構成 | 正答率 | 基準との差 [95%CI] |
| --- | --- | --- |
| **hybrid_budget（基準）** | **0.983** | — |
| retriever=dense | 0.917 | **-0.067 [-0.133, -0.017] 悪化** |
| retriever=sparse | 0.883 | **-0.100 [-0.183, -0.033] 悪化** |
| budget=1536 | 0.950 | -0.033 [-0.083, 0.000] |
| budget=4096 | 0.983 | 0.000 |
| rrf_k=10 / 120 | 0.967 | -0.017 [-0.050, 0.000] |

- **dense 単体も BM25 単体も有意に悪い。** 併用が効いている
- BM25 単体（0.883）が dense 単体（0.917）より悪いのは、語彙が
  重ならない質問を落とすため
- **`rrf_k` は 10〜120 でほとんど効かない。既定の 60 で十分。**
  触らなくてよい軸が分かったことが成果
- budget=4096 は 2560 と完全に同じ

## 人手検査

`rag review` で8タイプから11件を層別抽出して判定した結果、
**自動採点との一致率 1.00**。負例10件（もっともらしいが誤りの回答）も
全件が誤答と判定された。採点を緩めた後の値なので、緩めすぎていないことの確認になる。

正誤に現れない品質の指摘も得られた。

- 「内容は正しいが、手順の参照先の説明がなく不親切」
- 「原則の数だけでなく3原則の内容も併記されているとよい」

正答/誤答の2値では拾えない軸で、プロンプト設計で扱うべきもの。

## 未解決・次にやること

- **より弱いモデルでの比較。** 0.983 では手法差が出にくい。差が出る領域まで
  条件を厳しくしないと、リランカーやクエリ変換の効果を測れない
- **2モデル × 2環境**（設計の Phase 2 完了条件）。`gemma-4-e4b-it-qat` と
  `agents-a1-4b` の入手、環境1・環境2 へのアクセスが要る
- **実資料での検証。** このコーパスは構造が素直（見出しが取れる、表が単純）。
  実資料ではレイアウト崩れ・スキャンPDF・表の複雑さが出るはずで、
  Loader と table 型の質問が最初に壊れると予想する
- 表の短いセル（「4 中」）を引けない件。埋め込みでも BM25 でも手がかりが乏しい

## この実験からの一般的な教訓

1. **検索の改善は、それがプロンプトに届いて初めて精度になる。**
   検索指標だけを見ていると「検索は当たっているのに答えられない」という
   誤った結論に至る。`hit@k` と `context_hit` を分けて測る
2. **`top_k` / `chunk_size` / `context_token_budget` は独立に決められない。**
   3つを組で振る必要がある
3. **小さく刻めば多く入る、は成立しない。** チャンクを小さくすると
   マッチに必要な文脈が失われ、検索自体が悪化する
4. **gold は飽和する。** 1.000 に達したら、それ以上は測れない。
   ただし恣意的に難しい質問を作り続けても、実運用の役に立たない指標を
   最適化することになる
